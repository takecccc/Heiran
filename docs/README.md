# 設計文書の案内

`Heiran` の要件、仕様、設計、判断、確認の観点をまとめた文書の一覧。**仕様と設計の正は、この `docs/` にある。**
実装の状況は `CMakeLists.txt` の `heiran_core` に登録されたファイルを正とする。

## 読む順

初めて読むときは、上から順に読む。

| 文書 | 内容 | 種類 |
| --- | --- | --- |
| [要件定義](./要件定義.md) | 何を実現するか。要件ごとの状態 (済 / 一部 / 未 / 対象外) | 要件 |
| [アーキテクチャ設計](./アーキテクチャ設計.md) | 層の構成、主要なクラスの責務、データフロー | 設計 |
| [表示状態仕様](./表示状態仕様.md) | 表示状態、同期の更新規則、フィット | 仕様 |
| [座標と画素値の仕様](./座標と画素値の仕様.md) | 座標変換、選択矩形、画素値とルーペの表示、共有カーソル | 仕様 |
| [画像表示設計](./画像表示設計.md) | データの持ち方、表示の変換、キャッシュ、描画 | 設計 |
| [解析機能設計](./解析機能設計.md) | 解析ウィンドウ、共有選択範囲、ヒストグラム、変化グラフ、差分 | 設計 |

## 文書の役割

- **要件**は、何をするかを決める。実装の状態を併記する。
- **仕様**は、挙動を決める。実装とテストの正。挙動を変えたら、仕様を先に直す。
- **設計**は、仕組み (構成、持ち方、アルゴリズム) を決める。
- **判断**は、仕様と設計の理由を残す。仕様を読んで「なぜ」と思ったら、ここを読む。方針を変えたら、その項目を書き換える (古い決定は消す)。
- **テスト観点**は、確かめることを列挙する。ケースの名前 (`同期 Case 1` など) を、テストのコメントが参照する。

## 書くときの決まり

- 仕様と設計には、**今の決定**を書く。「初期実装では」「MVP では」といった当時の想定や、日付つきの注記を残さない。
- 同じ内容を、複数の文書に書かない。1 か所に書いて、ほかは参照する。
- 未着手の作業は [open_tasks.md](../open_tasks.md) に書く (要件定義には、状態だけを書く)。
- 作業のルールは [AGENTS.md](../AGENTS.md) にある。
- 利用者向けのマニュアルは、設計文書ではなく、[manual/](../manual/index.md) にある (アプリの Help > Manual から開く)。
